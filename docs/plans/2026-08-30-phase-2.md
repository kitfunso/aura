## Step 1: Session-start visible color (delayed VT via handed-over targets)
**Files:** `src/hook.js`, `src/adapters/frame-win.ps1`
**What:** Today colors appear only at the first prompt: the SessionStart VT delivery races Claude Code's TUI init and gets wiped. REVIEW FINDING (confirmed against frame-win.ps1:84-92): a fully detached spawn cannot fix this, because the console-ancestry walk only sees live processes and the hook's node parent is dead before PowerShell even starts - the chain is severed at hop 1. Design that survives it: keep the existing SYNC adapter spawn at SessionStart (the ancestor chain is alive there). The sync pass resolves the attach-target PID chain, paints DWM, prints the hwnd, and skips the immediate VT write; it then spawns a detached HIDDEN grandchild (`Start-Process -WindowStyle Hidden`, re-invoking the same script in a delayed-writer mode) handing over the resolved PID list. The grandchild sleeps ~2 s (past TUI init), re-reads state.json and SKIPS if `vtHex` is already set for the session (the user typed first - review finding 2), else attaches to the first accepting PID and writes. SessionStart also clears the session's cached `hwnd` + `vtHex` first, so a resumed session in a new tab re-handshakes and re-delivers. `vtHex` is still only marked from UserPromptSubmit. Known accepted race (review finding 4): opening two tabs very fast can hand the handshake the second tab; the allowlist caps the damage to terminal windows and the first prompt's fresh handshake self-heals it. Add `windowsHide: true` to the node spawn (review finding 3). The "session opens faster" claim is OUT: the sync spawn stays (~1 s once per session open); the gain is color before the first prompt.
**Verify:** Fire a fake SessionStart (no typing) at a live tab: tab + pane show the identity color ~2 s later (screenshot, pixel check), and no console window flashes. Type-first path: a prompt before the delay leaves the prompt-delivered color untouched (state shows `vtHex` set, grandchild skips). First prompt in a fresh session still works as before.
**Commit:** `feat: colors at session open via delayed VT with handed-over targets`

## Step 2: Rainbow hue-cycle frame for non-repo windows (SHIPPED, THEN REVERTED)
**Status 2026-08-30:** built, then removed the same day on Keith's ruling. No repo now means no color at all: the window keeps the terminal default. `rainbow-win.ps1`, the `rainbowPid` state key and the `rainbow` owner value are all gone. Do not rebuild this; see PRD "IS NOT" item 8.
**Files:** `src/adapters/rainbow-win.ps1`, `src/hook.js`, `src/state.js`
**What:** PRD post-MVP candidate 1. When identity is a bare folder (no git repo), spawn a detached PS loop against the handshook HWND: every 2 s advance hue ~12 degrees, HSV to RGB, repaint DWM border (+caption). Lifecycle rules, all three required: (a) exit when `IsWindow(hwnd)` fails; (b) exit after a 12 h cap; (c) yield to real sessions - the hook records `frameOwner[hwnd] = sessionId` in state.json on every paint, and the rainbow loop exits when another session owns the HWND. Review findings applied: BOTH the dedup guard and the owner record are keyed by HWND, never by session id (`rainbowPid[hwnd]` in state; two non-repo tabs in one window must share ONE loop, not fight), and the loop re-reads `frameOwner` immediately before EVERY DWM write with no sleep between check and write (a once-per-tick check leaves a 2 s blind spot that flashes over a repo session's paint).
**Verify:** Open a Claude session in a non-repo folder: border visibly drifts through hues (two screenshots ~6 s apart differ in border hue). Open a repo session in the SAME window: rainbow stops within one tick and the repo color holds. Close the window: the PS process exits (Get-Process check).
**Commit:** `feat: rainbow hue-cycle frame for non-repo sessions`
